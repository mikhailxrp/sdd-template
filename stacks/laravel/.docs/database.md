# Схема БД

> Этот файл — детальное описание всех таблиц.
> Агент читает его при планировании тасков, связанных с БД.
> Приводи в соответствие с `database/migrations/` (CORE-8): описание здесь — цель, миграции — способ её достичь. Расхождение — дефект, чинится новой миграцией или правкой этого файла, но не молча.

Типы указаны в синтаксисе Laravel Blueprint (PostgreSQL).

---

## Как устроен этот файл

Ниже — **ядро схемы**: то, что нужно любому проекту на этом стеке независимо от предметной области (пользователи, служебные страницы). Таблицы предметной области (каталог, заявки, корзина, заказы, оплата, интеграция с 1С, ИИ) приходят из включённых пакетов и вставляются в раздел «Таблицы пакетов» командой `sdd-capabilities` из `.docs/prd.md` → «Возможности».

При адаптации под проект:

- таблицы ядра обычно **не удаляют**, а расширяют колонками;
- специфичные для проекта таблицы добавляй в раздел «Дополнительные таблицы» по тому же формату (колонка | тип | назначение);
- миграции пишутся в порядке зависимостей: сначала родитель, потом потомок.

## Базовые таблицы

### `users`

| Колонка                | Тип                           | Назначение                                                                                                       |
| ---------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| id                     | `id()` bigint PK              |                                                                                                                  |
| name                   | `string(100)` NOT NULL        |                                                                                                                  |
| email                  | `string(150)` NOT NULL UNIQUE | хранится в нижнем регистре (приводится при сохранении), иначе в PostgreSQL `A@x.ru` и `a@x.ru` считаются разными |
| email_verified_at      | `timestamp()` NULL            |                                                                                                                  |
| password               | `string(255)` NOT NULL        | только хеш: cast `hashed`, никогда в открытом виде                                                               |
| role                   | `string(32)` NOT NULL         | cast в backed enum `App\Enums\UserRole`; разделение доступа к админке и кабинету                                 |
| remember_token         | `rememberToken()` NULL        |                                                                                                                  |
| created_at, updated_at | `timestamps()`                |                                                                                                                  |

> Значения `UserRole` и значение по умолчанию задаются в `.docs/prd.md` и блоках пакетов. Ядро гарантирует только значение `admin`: по нему `canAccessPanel()` пускает в Filament (допущение — подтвердить).
> Роль — строка с enum-cast, а не нативный `ENUM` PostgreSQL: менять набор значений нативного enum миграциями сложнее.

### `content_pages`

| Колонка                | Тип                               | Назначение                                            |
| ---------------------- | --------------------------------- | ----------------------------------------------------- |
| id                     | `id()` bigint PK                  |                                                       |
| slug                   | `string(160)` NOT NULL UNIQUE     | `/contacts`, `/delivery`, `/about` и т.п.             |
| title                  | `string(200)` NOT NULL            | заголовок страницы, выводится как `<h1>`              |
| body                   | `text()` NOT NULL                 | содержимое страницы                                   |
| is_published           | `boolean()` NOT NULL DEFAULT true | скрытая страница не выводится и не попадает в sitemap |
| seo_title              | `string(70)` NULL                 | если пусто — используется `title`                     |
| seo_description        | `string(160)` NULL                | если пусто — генерируется из первых слов `body`       |
| created_at, updated_at | `timestamps()`                    |                                                       |

> Статические страницы (контакты, доставка, о компании, юридические документы) редактирует администратор в Filament, а не разработчик в коде. Иначе правка текста требует деплоя.
> Формат `body` (Markdown или санитизированный HTML) фиксируется решением в `.docs/dev-log.md` до первой фазы с контентными страницами; до этого вывод только через `{{ }}` (CORE-9).

## Правило генерации SEO-полей

Применяется одинаково ко всем публичным сущностям (`content_pages` и таблицам пакетов, у которых есть `seo_title` / `seo_description`). Реализуется одним компонентом `<x-seo>` (`.docs/rules/seo.md`), не дублируется в каждом контроллере:

1. Если `seo_title` / `seo_description` заполнены — используются как есть
2. Если пусто — собираются по шаблону из данных сущности и из `config/` (название сайта, город), например для страницы: `"{title} — {site_name}"` (конкретный шаблон и значения берутся из настроек проекта, не хардкодятся)
3. Ни при каком варианте `<title>` и `<meta description>` не остаются пустыми: запасная ветка обязательна, недостаточно того, что поле есть в БД

## Дополнительные таблицы (примеры для расширения)

Не создаются по умолчанию. Это образец того, как добавлять таблицы под свой проект, не ломая соглашения ниже:

| Таблица        | Когда нужна                                                                                                                                               |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `redirects`    | при первой смене `slug` у опубликованной сущности: `id, old_path UNIQUE, new_path, created_at`, отдаёт 301 (`.docs/rules/seo.md`). Заранее не создавать |
| `settings`     | настройки, которые менеджер должен менять без деплоя: `id, key UNIQUE, value jsonb`                                                                       |
| `media`        | если файлам нужны собственные записи (подпись, `alt`, порядок): `id, disk, path, mime, size, alt`                                                         |
| `activity_log` | если нужен аудит действий менеджеров: `id, user_id FK, action, subject_type, subject_id, created_at`                                                      |

## Соглашения

- Первичный ключ каждой таблицы — `id()` (bigint); все таблицы имеют `timestamps()`
- Внешние ключи — `foreignId(…)->constrained()` с явным `onDelete`. Все `user_id` → `CASCADE`, **кроме** сущностей, история которых должна пережить удаление аккаунта (там `SET NULL`; исключение прописывается в описании таблицы)
- **PostgreSQL не создаёт индекс на внешний ключ автоматически** (в отличие от MySQL InnoDB). Индекс на каждый FK добавляется явно в миграции, иначе удаление и соединения по нему замедляются
- Время хранится в UTC (`APP_TIMEZONE=UTC`, CORE-11). Колонки времени — `timestamp()`
- Статусы и типы — строковая колонка + backed enum cast в модели, не нативный `ENUM` PostgreSQL. Допустимые переходы статуса проверяет одна Action (`general.md`)
- Булевы значения — `boolean()`; в БД не `0/1`-числа и не строки
- Деньги — только `DECIMAL` или целое в минимальных единицах, никогда `float`/`double` (`general.md`). Выбор фиксируется здесь при появлении первой денежной колонки: `< DECIMAL(12,2) | integer, копейки >`
- Пароли и токены — только хеши и зашифрованные значения; в открытом виде не хранятся
- Публично индексируемые сущности (у которых отдельный URL) имеют `slug` (UNIQUE), `seo_title`, `seo_description` (NULL) и флаг публикации `is_published`. Новую публичную таблицу без этого набора не добавлять
- Физически записи публичных сущностей не удаляются без причины: скрываются флагом публикации. `SoftDeletes` включается для таблицы только если это отмечено в её описании
- Поиск по тексту — только через индекс (`GIN` по `tsvector`, конфигурация `russian` — допущение, подтвердить). `ILIKE '%…%'` обычным индексом не обслуживается и на десятках тысяч строк деградирует
- Любой список — с пагинацией. На глубоких страницах (большой `OFFSET`) использовать `cursorPaginate()` вместо `paginate()`: смещение растёт, и запрос линейно замедляется
- Расширения PostgreSQL подключаются миграцией (`CREATE EXTENSION IF NOT EXISTS …`) и только теми пакетами, которым они нужны. Права на создание расширений на хостинге проверяются до старта фазы
- Кодировка БД — UTF8. Регистр в PostgreSQL учитывается при сравнении строк: учитывай это в уникальных полях и поиске
