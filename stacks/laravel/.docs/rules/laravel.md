Этот файл раскрывает правила `CORE-N` из `AGENTS.md`: контракты слоёв, примеры, настройки. Сами правила здесь не повторяются — при расхождении побеждает `AGENTS.md`. Правила включённых пакетов дополняют этот файл и не отменяют его.

## Базовые принципы

- Сначала штатные средства Laravel (Form Request, Policy, Job, Scheduler, Storage, RateLimiter), потом свой код. Собственную авторизацию, очередь, роутер или валидатор не писать
- Файлы создавать через `php artisan make:*`, а не вручную
- Логика и HTML не смешиваются: логика в Actions, HTML в Blade
- Именованные аргументы при вызове методов Laravel/Filament/Livewire не использовать — их имена не входят в гарантии обратной совместимости. Для собственных методов проекта допустимо

## Actions (CORE-1)

- Расположение: `app/Actions/<Domain>/<VerbNoun>.php`, например `app/Actions/Requests/SubmitRequest.php`
- Один публичный метод `handle()` с типизированными параметрами и возвратом. Принимает примитивы, модели или DTO, но не `Request` и не `Livewire`-компонент
- Если операция меняет больше одной таблицы — вся запись внутри `DB::transaction()` в самой Action
- Action может вызывать другую Action. Цикличные вызовы запрещены
- Возвращает результат (модель, значение) или бросает типизированное исключение. Редиректы, HTML и flash-сообщения — забота вызывающего слоя
- Побочные эффекты (письмо, внешний вызов) Action не выполняет сама, а ставит Job в очередь (CORE-7)

Контракт:

```php
final class SubmitRequest
{
    public function handle(RequestData $data): Request
    {
        return DB::transaction(function () use ($data): Request {
            $request = Request::create($data->toArray());
            NotifyManagers::dispatch($request->id);   // Job, ставится в очередь

            return $request;
        });
    }
}
```

## Контроллеры и Form Requests (CORE-3, CORE-4)

- Метод контроллера: принять Form Request → вызвать Action → вернуть view или redirect. Больше ничего
- `authorize()` в Form Request проверяет права через Policy (`$this->user()->can(…)`), а не возвращает `true` по умолчанию
- Имена: `Store<Model>Request`, `Update<Model>Request`
- Внутри метода использовать `$request->validated()`; `$request->all()` и `$request->input()` для записи в БД запрещены
- POST публичной части заканчивается redirect (Post/Redirect/Get)

## Livewire

- Компонент держит только состояние интерфейса; бизнес-операции вызывает через Action
- Публичные свойства компонента клиент может изменить. Идентификаторы защищать атрибутом `#[Locked]` (проверить в документации Livewire 4)
- В каждом методе-обработчике, который меняет данные, — валидация (`$this->validate()`) и проверка прав (`$this->authorize()`). Нельзя полагаться на то, что кнопка скрыта в шаблоне
- Тяжёлые выборки не выполнять в `render()` без пагинации и жадной загрузки связей

## Модели и данные (CORE-2, CORE-5, CORE-10, CORE-11)

- Eloquent: связи, scopes, casts, enums, `$fillable`. Бизнес-логика и вызовы внешних систем в моделях запрещены
- Статусы и типы — backed enums (`app/Enums`) + cast в модели; строковые константы статусов в коде не разбросаны
- В `AppServiceProvider::boot()` включить строгий режим вне прода: `Model::shouldBeStrict(! app()->isProduction())` (закрывает ленивую загрузку, молчаливый сброс атрибутов и обращение к несуществующим)
- Инварианты защищаются в БД, а не только в коде: внешние ключи, `unique`, `not null`, `check`. Валидация в коде — это удобство для пользователя, не защита
- Счётчики и остатки (всё, что читают и затем уменьшают/увеличивают) — только условным `UPDATE … WHERE …` или `lockForUpdate()` внутри транзакции. Схема «прочитал → посчитал → записал» без блокировки запрещена: два параллельных запроса дают гонку
- `SoftDeletes` включается для таблицы только если это зафиксировано в `.docs/database.md`
- Индексы: на внешние ключи и на поля, по которым фильтруют или сортируют в публичных списках

### Миграции (CORE-8)

- Одна миграция — одна цель. Имя описывает действие: `add_status_to_requests_table`
- На проде не использовать `migrate:rollback` и `migrate:fresh`; исправление ошибки — новой миграцией
- Миграция не зависит от моделей и Actions: за время жизни проекта они изменятся, а миграция должна работать всегда
- Сидеры справочников и ролей идемпотентны (`updateOrCreate`) — повторный запуск не плодит дубли

## Очереди, Jobs, расписание (CORE-7)

- Job реализует `ShouldQueue` и вызывает Action. Своей бизнес-логики не содержит
- В конструктор передавать идентификаторы и скаляры, актуальное состояние перечитывать внутри `handle()`
- У каждого Job заданы `$tries` и `$backoff`, реализован `failed()` с записью в лог. Для Jobs, которые нельзя выполнять параллельно, — `ShouldBeUnique` или `WithoutOverlapping`
- Идемпотентность: повторный запуск проверяет текущее состояние (например, письмо уже отправлено) и ничего не дублирует
- Расписание — только в `routes/console.php`. Долгим задачам — `->withoutOverlapping()`
- Воркер на проде запускается под supervisor/systemd с автоперезапуском; после деплоя — `php artisan queue:restart`

## Blade и фронтенд (CORE-9)

- В Blade нет запросов к БД и бизнес-условий. Права — через `@can` (Policy)
- Повторяющийся блок 2+ раза → Blade-компонент в `resources/views/components/`
- Формы: `@csrf`, `old()` для повторного показа, ошибки через `@error`
- Ассеты подключать через `@vite`, ссылки — через `route()`, а не вручную собранные URL
- Санитайзер для `{!! !!}` выбирается решением в `.docs/dev-log.md`, до этого `{!! !!}` не использовать (допущение — подтвердить)

## Filament (CORE-4, CORE-14)

- Resource описывает интерфейс: формы, таблицы, фильтры. Операции с бизнес-смыслом (сменить статус, применить обмен) вызывают Action
- Filament применяет Policies модели. Resource без Policy запрещён
- Доступ в панель — `canAccessPanel()` в модели `User` (контракт `FilamentUser`). Роли и права — по правилу CORE-4
- Колонки таблицы, которые показывают связи, требуют жадной загрузки этих связей. Иначе N+1 (CORE-10)
- Точные API (хуки форм, действия, модификаторы запроса) сверять с документацией Filament 5 перед написанием, не по памяти

## Безопасность (CORE-3…6, CORE-12, CORE-13)

- Авторизация — штатные средства Laravel. Сообщение при неверном входе одинаково для «неверный пароль» и «нет такого пользователя»
- Минимальная длина пароля — 8 символов, задаётся через `Password::min(8)`. Дополнительные требования — только если их требует prd
- Лимиты: именованные лимитеры (`RateLimiter::for(…)`) для входа и публичных форм, подключаются middleware `throttle:<name>`. Нарушения лимитов и неудачные входы пишутся в лог (`Log::warning`)
- Cookies сессии на проде: `SESSION_SECURE_COOKIE=true`, `SESSION_HTTP_ONLY=true`, `SESSION_SAME_SITE=lax`. Требует HTTPS. Без HTTPS сессия не будет работать
- Заголовки безопасности (`X-Content-Type-Options: nosniff`, `Referrer-Policy`, защита от встраивания во фрейм) — один middleware `SecurityHeaders`, регистрируется в `bootstrap/app.php`. Строгий `Content-Security-Policy` с `script-src` не вводить без проверки Livewire и Filament, которые используют инлайн-скрипты (допущение — проверить)
- HSTS и редирект на HTTPS — на уровне nginx
- Загрузки: правила `mimes`/`mimetypes` + `max`, имя файла в хранилище генерирует Laravel (`store()`), оригинальное имя хранится в БД как данные. Доступ — через `Storage` и подписанные URL или `storage:link`
- Поля с секретами в моделях (`token`, `api_key`, `password`) — в `$hidden`. В логи не писать пароли, токены, ключи API и тела запросов с ними
- Вебхуки и входящий API — только через `routes/api.php` и только с проверкой подписи; подробности в блоке пакета, который их вводит

## Тестирование (CORE-15, CORE-16)

- Pest 4; запуск: `vendor/bin/pest`. Структура: `tests/Feature` (потоки, HTTP, Livewire, права) и `tests/Unit` (чистая логика Actions)
- Тестовая БД — PostgreSQL той же версии, что на проде, с `RefreshDatabase`. SQLite в тестах не используем: поведение отличается (допущение — подтвердить)
- Внешние системы подменять штатными fake: `Http::fake()`, `Queue::fake()`, `Mail::fake()`, `Storage::fake()`. Базу данных не мокать
- Обязательные проверки для каждого проекта: гость не попадает в админку; пользователь без прав получает 403 (Policy); публичная форма ограничена `throttle`; Action пишет данные атомарно
- Фабрики на каждую модель в `database/factories/`
- Что не покрывается автотестами и проверяется вручную по `.docs/dod-global.md`: вёрстка, адаптивность, визуальная часть Filament

## Обработка ошибок

- Оператор `@` не использовать. Пустой `catch` запрещён
- Пользователь видит понятное сообщение, лог получает полную трассировку. На проде `APP_DEBUG=false`
- Логи пишутся в канал `daily` (`storage/logs/`). Контекст логов без секретов
- Ошибки внешних систем и Jobs логируются с идентификатором связанной сущности; пользовательское сообщение не содержит деталей чужого сервиса

## Code style

- Laravel Pint с пресетом `laravel`, без `pint.json`. Запуск: `vendor/bin/pint`
- `declare(strict_types=1)` в каждом новом файле, типизированные свойства, параметры и возвращаемые значения
- `match` вместо `switch`, enums вместо строковых констант, `final` для Actions и Jobs
- Имена: Actions — `VerbNoun`; Policies — `<Model>Policy`; Form Requests — `Store<Model>Request`; Jobs — глагол + объект; таблицы — snake_case во множественном числе; модели — единственное число
