Правила для публичной части сайта. Админка (Filament) не индексируется и под эти правила не подпадает. Типы страниц и схемы schema.org, специфичные для предметной области, описаны в блоках включённых пакетов.

## Мета-теги

- `<title>` и `<meta name="description">` никогда не пишутся руками во view. Они выводятся одним Blade-компонентом `<x-seo>` в основном layout, на каждой публичной странице ему передаётся сущность (`:entity`)
- Компонент берёт значения по единому приоритету: колонки `seo_title` / `seo_description` сущности, если заполнены → шаблонный запасной вариант, если пусты. Пустую строку компонент не возвращает никогда — запасная ветка обязательна
- Запасной шаблон собирается только из данных, которые уже есть у сущности (название, раздел) и из `config/` (название сайта, город). Тексты, которых у сущности нет, не выдумывать
- Каждая публичная сущность со своей страницей имеет колонки `seo_title`, `seo_description` (nullable) и `slug` (unique). Состав фиксируется в `.docs/database.md`
- Один `<h1>` на странице, совпадающий с названием сущности (`name`/`title`). Второй, иначе сформулированный `<h1>` «для красоты» не писать
- `<h2>`/`<h3>` следуют структуре содержания, а не размеру шрифта. Нужный внешний вид задаётся классами Tailwind

## Структурированные данные (schema.org)

- Разметка выводится как JSON-LD в `<script type="application/ld+json">` только через директиву `@json(…)`. Не собирать JSON строкой вручную и не выводить через `{!! !!}` (CORE-9). Параметры экранирования по умолчанию у `@json` оставлять (проверить в документации Blade)
- Тип schema.org и обязательные поля для каждого типа страницы задаются в блоке пакета, который вводит эту страницу
- Значения в разметке и видимый на странице текст берутся из **одной и той же** переменной (цена, наличие, название, адрес). Никогда не вычислять дважды. Расхождение разметки и видимого текста хуже, чем отсутствие разметки (`dod-global.md`, раздел SEO)
- Страницы вложенных разделов выводят `BreadcrumbList`. Он строится из той же цепочки родителей, что и видимые «хлебные крошки»: один источник, два вывода

## URL и маршрутизация

- Каждая публичная сущность открывается по `slug`, а не по числовому id в URL (`/catalog/divany`, не `/product?id=42`). Привязка через route model binding по `slug` (`getRouteKeyName()`)
- `slug` генерируется из названия при создании (`Str::slug`), редактируется вручную в админке и после публикации автоматически не меняется
- Отфильтрованные и отсортированные представления (`?sort=price&color=red`) выводят `<link rel="canonical">` на чистый URL раздела. Canonical строится в одном месте — в `<x-seo>` через `url()->current()` (без query-параметров), а не прописывается во view. То же правило для фильтров Livewire, попадающих в URL (`#[Url]`)
- Смена `slug` (переименовали сущность, перестроили разделы) не должна молча ломать старый URL: 301-редирект старого `slug` на новый через таблицу `redirects`. Таблицу создавать миграцией только когда впервые происходит смена `slug`, заранее не строить

## Sitemap и robots

- `/sitemap.xml` — реальный маршрут (`routes/web.php`) с контроллером, который читает опубликованные сущности из БД. Статический файл запрещён: если он не отражает текущее состояние БД, он вводит в заблуждение, а не просто устарел
- Сгенерированный sitemap кэшируется (`Cache`), кэш сбрасывается при изменении публикуемого контента (из Action, которая меняет контент) и по расписанию (`routes/console.php`). Полный перебор таблиц при каждом заходе краулера недопустим
- Если URL больше 50 000, sitemap разбивается на файлы с индексным sitemap
- Пакет для sitemap подключать только решением в `.docs/dev-log.md`; по умолчанию — свой контроллер
- Каждый URL в sitemap отдаёт 200. Неактивные, неопубликованные и скрытые сущности в запрос sitemap не попадают — это баг, а не мелочь
- `public/robots.txt` — статический файл. Содержит: `Disallow: /admin/` (путь панели Filament), служебные пути включённых пакетов (их блоки добавляют свои строки) и строку `Sitemap: https://<домен>/sitemap.xml`. Каталог со сборкой ассетов (`/build/`) не закрывать — краулеру нужны CSS и JS для отрисовки
- Вне production сайт отдаёт `X-Robots-Tag: noindex` (middleware, условие по `APP_ENV`), чтобы тестовая копия не попала в индекс

## Рендеринг контента (GEO)

- Текст публичных страниц рендерится на сервере и приходит в первом HTML-ответе. Никогда не подгружать его через JS-запрос, заполняющий DOM после загрузки. Большинство AI-краулеров, в отличие от Googlebot, JS не выполняют: если описание есть только после `fetch()`, для них его нет
- Livewire-компоненты рендерятся на сервере при первой загрузке, но контент, важный для SEO, нельзя отдавать через `lazy`, `wire:init` и отложенную загрузку: его не будет в начальном HTML
- Структурированные характеристики сущности (материал, размер, вес и т.п.) выводятся списком `<dl>` или таблицей пар «свойство — значение», а не вшиваются в текст описания. Хранить их отдельными полями или записями, не дописывать в `description`: факт проще извлечь из строки таблицы, чем из абзаца
- Если факт встречается на странице в двух местах (значение в schema.org, видимый текст, таблица характеристик), он берётся из одной переменной и выводится дважды. См. «Структурированные данные» — то же правило, повторённое, потому что ломается именно здесь

## Изображения

- У каждого `<img>` непустой `alt`, описывающий содержимое: название сущности плюс отличительная деталь, если она известна (цвет, вариант). Не имя файла и не пустая строка
- Если у изображения есть собственная запись в БД (медиа-библиотека), поле `alt` у неё есть, а при пустом значении подставляется название сущности
- Чисто декоративные изображения (иконки рядом с видимым текстом, разделители) получают `alt=""` явно: пустой атрибут — осознанный выбор, отсутствующий — нет
