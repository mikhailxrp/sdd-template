# Формат capability-пакета

Этот файл описывает, как писать пакеты в `capabilities/*.md`. Читает автор пакета и команда `/sdd-capabilities`. После первой сборки папка `capabilities/` удаляется из проекта целиком (см. «Жизненный цикл»).

## Что такое пакет

Пакет — самодостаточный блок требований одной возможности проекта (каталог, заявки, оплата, обмен с 1С, ИИ). Ядро стека (`AGENTS.md`, `laravel.md`, `general.md`, `seo.md`, `database.md`, `dod-global.md`) о предметной области ничего не знает. Всё предметное приходит из пакетов, которые `.docs/prd.md` → «Возможности» отметил как «вкл».

Выключенного пакета в проекте нет: ни его правил, ни таблиц, ни пунктов DoD.

## Жизненный цикл

Команда `/sdd-capabilities` запускается после `/sdd-init` (роли и разделы §1–2 уже в `prd.md`) и до `/sdd-schema`. Режимы:

| Режим | Что делает |
|-------|------------|
| `init` (первый запуск) | Читает таблицу «Возможности» из `prd.md`, выполняет «Проверки при сборке», вставляет блоки включённых пакетов в `AGENTS.md`, `database.md`, `dod-global.md`, создаёт `.docs/capabilities.md`. Затем, после успешных проверок и подтверждения человека, **удаляет папку `capabilities/`** |
| `add <name>` | Добавляет пакет в уже собранный проект: блоки вставляются так же, строка в `prd.md` меняется на «вкл», причина записывается в `.docs/dev-log.md` |
| `remove <name>` | Удаляет блоки пакета по маркерам. Таблицы БД уже могли быть созданы: удаление блока из `database.md` таблицы не удаляет, для этого нужна отдельная миграция отдельной фазой (CORE-8) |

### Почему папку удаляем

- В проекте остаются только правила включённых пакетов: поиск по репозиторию и агент не натыкаются на правила невключённых (например, оплаты), и они не «просачиваются» в код.
- Папка в репозитории клиента — шум.
- Потерять ничего нельзя: `sdd-new-project.ps1` делает первый коммит **до** сборки, значит все пакеты в нём лежат.

### Откуда `add` берёт файл пакета

1. `capabilities/<name>.md`, если папка ещё есть
2. Иначе из первого коммита проекта: `git show $(git rev-list --max-parents=0 HEAD):capabilities/<name>.md`
3. Иначе (проект создан с `-NoGit`) команда просит указать файл из `sdd-template/stacks/laravel/capabilities/` и копирует его на время сборки

Пакет берётся в версии на момент создания проекта. Если нужна более новая версия из шаблона, человек явно указывает файл из `sdd-template` (вариант 3).

## Файл пакета

Один пакет — один файл `capabilities/<name>.md`. Имя в нижнем регистре через дефис (`cart-checkout`, `onec-sync`).

### Шапка (YAML)

```yaml
---
name: catalog
prefix: CAT
title: Каталог товаров
status: ready          # ready | stub
requires: []           # пакеты, без которых этот не работает
conflicts: []          # пакеты, взаимоисключающие по умолчанию
critical: false        # true = блок DoD приравнивается к «Данные» и «Безопасность»
---
```

| Поле | Правило |
|------|---------|
| `name` | Совпадает с именем файла и со строкой в таблице `prd.md` |
| `prefix` | 2–5 заглавных букв, уникален среди пакетов и не равен `CORE` |
| `status` | `stub` = заготовка без содержания. Сборка не включает такой пакет, а сообщает, что его нужно сначала заполнить |
| `requires` | Если пакет включён, а требуемый нет — сборка останавливается |
| `conflicts` | Включить оба можно только с обоснованием в `prd.md` → «Возможности» |
| `critical` | Если `true`, блок DoD начинается с пометки «Критично: непройденный пункт = таск не принят» |

### Разделы пакета

Заголовки строго такие, по ним сборка находит блоки. Для пакетов со `status: stub` обязательны только шапка и раздел «Что нужно выяснить перед написанием».

| Раздел | Обязателен | Куда вставляется при сборке |
|--------|-----------|------------------------------|
| `## Параметры` | да | Не вставляется: сборка использует его, чтобы спросить у человека недостающие значения и заполнить колонку «Параметры» в `prd.md` |
| `## Правила` | да | `AGENTS.md` → «Правила пакетов», блок `### <title>` |
| `### Исключения из правил ядра` (внутри «Правил») | если нужны | Там же, внутри блока пакета |
| `## Каталоги` | если пакет добавляет код | Подблок `#### Каталоги` внутри блока пакета в «Правилах пакетов» (дерево ядра не правится, так сказано в `AGENTS.md`) |
| `## SEO` | если пакет вводит публичные страницы | Подблок `#### SEO` внутри блока пакета |
| `## Таблицы БД` | если пакет добавляет таблицы | `.docs/database.md` → «Таблицы пакетов» (порядок зависимостей) и фрагмент связей в «Карту связей» |
| `## DoD` | да | `.docs/dod-global.md` → «Блоки пакетов» |
| `## Проверки аудита` | да | `.docs/capabilities.md` (читают команды `audit-*`) |
| `## Фазы` | да | `.docs/capabilities.md` (читает `sdd-roadmap`) |
| `## С другими пакетами` | если есть взаимодействие | Только записи для пакетов, включённых в проекте; вставляются в тот же блок «Правил» |

`.docs/capabilities.md` создаётся сборкой. В начале — состав сборки (дата, список включённых пакетов, источник каждого пакета), затем по каждому пакету подсказки для роадмапа и проверки аудита.

Строки для `public/robots.txt` и разметка из раздела `## SEO` в файлы приложения сборкой не вносятся: их реализует фаза, которая вводит соответствующие страницы.

## Маркеры блоков

Каждый вставленный блок оборачивается парой маркеров:

```
<!-- capability:<name>:begin -->
… содержимое блока …
<!-- capability:<name>:end -->
```

- Маркеры ставятся в `AGENTS.md`, `database.md`, `dod-global.md` и `.docs/capabilities.md`
- Всё между маркерами принадлежит сборке: ручные правки там пропадут при следующем `add` / `init`. Проектная специфика пишется вне маркеров: в `AGENTS.md` после блоков пакетов, под заголовком `### Правила проекта`
- `remove <name>` удаляет блок от `begin` до `end` включительно
- Плейсхолдеры-якоря `<!-- sdd-capabilities: … -->` в ядре **остаются** на своих местах: это точки вставки для `add`. Блоки вставляются сразу после якоря в порядке зависимостей
- Таблица «Возможности проекта» в `AGENTS.md` — сводная: она целиком пересобирается из `prd.md`, маркеров не имеет

## Требования к содержимому

### Параметры

Таблица `параметр | зачем | пример`. Это то, что должен решить человек до сборки (провайдер, формат обмена, получатели заявок). Не угадывать, а спрашивать. Всё, чего автор пакета не знает, помечать `(проверить в документации <сервиса>)`.

### Правила

- Нумерация `<PREFIX>-N`, например `CAT-1`
- Формат как у `CORE-N`: конкретно, проверяемо, со словами «только», «никогда», «всегда»
- Не повторять правила ядра. Нужно сослаться: «по `CORE-7`»
- Правило ядра не отменяется. Исключение допускается только подразделом `### Исключения из правил ядра` в виде «`CORE-N`: что разрешено, где и при каких условиях». Ядро на такие исключения ссылается (например, `CORE-2` про сырой SQL)
- Нельзя выдумывать специфику внешних систем (формулы подписей, эндпоинты, форматы), если автор в ней не уверен: ставить `(проверить в документации <сервиса>)` и указывать, перед какой фазой это проверить
- Известные подводные камни интеграций записываются сразу
- Текст пакета не ссылается на файлы папки `capabilities/`: после сборки их в проекте нет

### Таблицы БД

- Тот же формат, что в `database.md` ядра: `колонка | тип Blueprint | назначение`, затем индексы и внешние ключи с `onDelete`
- Индекс на каждый внешний ключ указан явно (PostgreSQL не создаёт его сам)
- Публичные сущности имеют `slug`, `seo_title`, `seo_description`, `is_published` (соглашения `database.md`)
- Каждая таблица используется хотя бы в одном правиле, DoD или сценарии; таблица «на всякий случай» не добавляется
- Порядок: родитель раньше потомка. Ссылки на таблицы другого пакета только при наличии его в `requires`

### SEO

Для каждого типа публичной страницы: тип schema.org и обязательные поля; пути для `robots.txt` (`Disallow`); что попадает в sitemap.

### DoD

- Пункты в формате `- [ ] …`, проверяемые вручную или командой
- Только то, чего нет в `dod-global.md` ядра
- Если `critical: true`, пункты описывают то, от чего зависят деньги или данные клиента

### Проверки аудита

Короткий список того, что должны проверить команды `audit-security`, `audit-functional` и `audit-integration` именно для этого пакета.

### Фазы

Подсказки для `sdd-roadmap`: с какого вертикального среза начать (что можно показать клиенту), какая часть самая рискованная и идёт ранней фазой с тестами внутри неё, что можно делать параллельно.

### С другими пакетами

Записи вида «Если включён `<name>`: …». Пакет не должен ссылаться на пакеты, которых нет в его `requires`, вне этого раздела.

## Заготовки (`status: stub`)

Заготовка содержит только шапку и раздел «Что нужно выяснить перед написанием»: список вопросов и источников документации. Правил, таблиц и DoD в ней нет, потому что содержание нельзя придумывать без сверки с документацией провайдера.

## Шаблон нового пакета

````markdown
---
name: <name>
prefix: <PFX>
title: <Название>
status: ready
requires: []
conflicts: []
critical: false
---

# <Название>

< 1–2 предложения: что даёт пакет проекту >

## Параметры

| Параметр | Зачем | Пример |
|----------|-------|--------|

## Правила

1. **<PFX>-1.** …

### Исключения из правил ядра

- `CORE-N`: …

## Каталоги

```
app/Actions/<Domain>/   → …
```

## Таблицы БД

### `<table>`

| Колонка | Тип | Назначение |
|---------|-----|------------|

**Индексы:** …

## SEO

| Страница | schema.org | Обязательные поля | robots / sitemap |
|----------|------------|-------------------|------------------|

## DoD

- [ ] …

## Проверки аудита

- …

## Фазы

- …

## С другими пакетами

- Если включён `<name>`: …
````

## Проверки

### При сборке (выполняет `/sdd-capabilities`, пока папка `capabilities/` существует)

1. Каждая строка таблицы «Возможности» соответствует файлу `capabilities/<name>.md`
2. У включённых пакетов `status: ready`
3. `requires` выполнены; конфликты либо отсутствуют, либо обоснованы в `prd.md`
4. Префиксы уникальны, номера правил идут подряд без пропусков
5. Таблицы, на которые ссылаются правила и DoD, описаны в разделе «Таблицы БД» этого пакета или пакета из `requires`
6. Исключения из `CORE-N` в пакетах ссылаются на существующие номера правил ядра

### После сборки (выполняет `check_sdd.py`, папки `capabilities/` уже нет)

1. Для каждой строки «вкл» в `prd.md` есть пара маркеров `capability:<name>` во всех файлах, куда пакет вставляет блоки; для строк «выкл» маркеров нет
2. Маркеры парные: у каждого `begin` есть `end`
3. Папка `capabilities/` отсутствует (после `init`)
4. Якоря `<!-- sdd-capabilities: … -->` на месте
5. Номера правил `<PREFIX>-N` в `AGENTS.md` идут подряд, ссылки на `<PREFIX>-N` в `dod-global.md` и `capabilities.md` указывают на существующие правила
