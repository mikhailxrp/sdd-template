# WordPress (PHP 8.1+): детальные правила

Конкретизация правил `CORE-1`..`CORE-14` из `AGENTS.md`. Не изобретай несуществующие хуки, функции или поведение WordPress — при сомнении проверяй официальную документацию.

---

## 1. Архитектура темы и `functions.php` (`CORE-2`)

- **Никакой бизнес-логики в шаблонах** (`front-page.php`, `page.php`, `single.php`, `archive.php`, `template-parts/*.php`). Шаблон только получает подготовленные данные и выводит экранированный HTML.
- **`functions.php` используется только для:**
  - регистрации хуков и фильтров (`add_action`, `add_filter`)
  - подключения модулей (`require_once get_template_directory() . '/inc/...'`)
  - базовой инициализации темы
- **Вся бизнес-логика темы живёт в `/inc`**, по принципу «один файл = одна ответственность»:
  - `inc/setup.php` — `add_theme_support()`, меню, размеры изображений, загрузка text-domain
  - `inc/assets.php` — подключение CSS и JS
  - `inc/redux-config.php` — секции опций и метабоксы Redux Framework
  - `inc/ajax.php` — AJAX-обработчики
  - `inc/template-tags.php` — функции вывода повторяющихся элементов
  - `inc/template-functions.php` — фильтры `body_class`, хуки шаблонов
- Избегай жёсткой связанности между файлами в `inc/`.

## 2. PHP 8.1+, WPCS и стиль кода (`CORE-14`)

- Используй возможности **PHP 8.1+** там, где они улучшают читаемость (типизация параметров/возвратов, `match`, named arguments, nullsafe `?->`, union types).
- Следуй **WordPress Coding Standards (WPCS)** (пробелы внутри скобок, Yoda conditions где требует конфиг `phpcs.xml.dist`, PHPDoc для функций и хуков).
- Всегда проверяй изменённые файлы через `php -l` (и `phpcs`, если установлен).
- В начале каждого PHP-файла (кроме шаблонов с прямым вызовом из WP, но и там не вредит) защищай от прямого доступа:
  ```php
  if ( ! defined( 'ABSPATH' ) ) {
      exit;
  }
  ```

## 3. Экранирование вывода и санитизация входа (`CORE-4`, `CORE-5`)

- **Вывод:** экранируй **всё**, всегда, в точке вывода (late escaping):
  - текст: `esc_html()`, `esc_html__()`, `esc_html_e()`
  - атрибуты HTML: `esc_attr()`, `esc_attr__()`, `esc_attr_e()`
  - URL: `esc_url()`
  - контролируемый HTML (например, контент редактора/Redux WYSIWYG): `wp_kses_post()`
  - Никогда не выводи неэкранированные переменные.
- **Вход:** никогда не доверяй `$_POST`, `$_GET`, `$_REQUEST` или параметрам REST/AJAX напрямую. Всегда применяй `wp_unslash()` + подходящий санитайзер:
  - строки: `sanitize_text_field()`, `sanitize_textarea_field()`
  - целые положительные ID/счётчики: `absint()`
  - email: `sanitize_email()` + `is_email()`
  - URL: `esc_url_raw()`
  - ключи/слаги: `sanitize_key()`, `sanitize_title()`

## 4. Безопасность: Nonces, права и `$wpdb` (`CORE-6`, `CORE-7`)

- **Nonces:** каждая форма и каждое изменяющее состояние действие (POST, AJAX) обязаны иметь nonce:
  - в форме: `wp_nonce_field( '<action>', '<name>' )` + проверка `wp_verify_nonce()`
  - в AJAX: `wp_create_nonce()` через `wp_localize_script()` + проверка `check_ajax_referer()` в самом начале обработчика
- **Права доступа:**
  - всегда проверяй `current_user_can( '<capability>' )` перед любыми административными или изменяющими чужие данные операциями
  - в REST API (`register_rest_route`) всегда задавай явный `permission_callback` (для публичных эндпоинтов — `__return_true` только с обоснованием, для защищённых — `current_user_can(...)`)
- **База данных (`$wpdb`):**
  - **Запрещены** сырые PDO и `mysqli_*`
  - Любые кастомные SQL-запросы выполняются только через глобальный `$wpdb` с `$wpdb->prepare()`
  - **Никогда** не конкатенируй переменные прямо в SQL-строку, даже внутри `$wpdb->prepare()` (имена таблиц берутся из `$wpdb->prefix . 'table_name'`, значения — только через плейсхолдеры `%d`, `%s`, `%f`, идентификаторы в WP 6.2+ — через `%i`)

## 5. Плагины (`CORE-3`)

- Логика плагина **никогда** не кладётся в тему (иначе смена темы ломает данные и функциональность).
- Каждый кастомный плагин обязан:
  - иметь корректный заголовок плагина (`Plugin Name:`, `Version:`, `Text Domain:`, `Requires PHP:`)
  - содержать защиту `if ( ! defined( 'ABSPATH' ) ) { exit; }`
  - использовать **уникальный префикс** для всех функций, хуков, констант, классов/неймспейсов и опций

---

## 6. Тема, ассеты и локализация (`CORE-8`, `CORE-9`)

- Подключай CSS и JS **только** через `wp_enqueue_style()` и `wp_enqueue_script()` внутри хука `wp_enqueue_scripts`.
- Никаких `<link>` и `<script>` напрямую в `header.php`, `footer.php` и других шаблонах.
- Для URL ассетов используй `get_stylesheet_directory_uri()` (работает и для дочерней темы).
- Всегда передавай явный `$version` (`filemtime( get_stylesheet_directory() . '/assets/...' )` или константу версии темы) для cache busting.
- Переиспользуемые фрагменты разметки выноси в `template-parts/` и подключай через `get_template_part( 'template-parts/...', null, $args )` (передача данных третьим аргументом WP 5.5+ или `set_query_var()`). Избегай дублирования разметки.
- Все пользовательские строки интерфейса оборачивай в `__()`, `_e()`, `esc_html__()`, `esc_attr__()` с text-domain темы — никогда не хардкодь текст напрямую в шаблонах.

## 7. Redux Framework (кастомные поля и повторители) (`CORE-12`)

- Для кастомных полей, опций темы и повторителей используется **Redux Framework** (metaboxes / options), **не ACF**.
- Конфигурация опций и метабоксов хранится в `inc/redux-config.php` (или разбивается на файлы в `inc/redux/`).
- В шаблонах значения опций/метаполей всегда читаются через хелпер с проверкой существования ключа и безопасным значением по умолчанию (чтобы сайт не падал с fatal/warning, если плагин Redux временно деактивирован), и экранируются при выводе (`CORE-4`).
