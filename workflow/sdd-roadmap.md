## Принцип нарезки

Сначала вертикальный срез до ценности (то, что можно показать),
потом обвязка — тот же принцип, что в phase-example.md стартера.

**Приоритет из раздела 3.1 ТЗ определяет крупность фаз:**

- приоритет «срок» → тонкие фазы, MVP-ядро отдельно от остального
- приоритет «объём» → можно резать крупнее, по модулям целиком
- приоритет «бюджет» → сначала самое дешёвое к пропуску без потери
  ценности, дорогие интеграции — отдельными поздними фазами
  (проще исключить фазу целиком, чем недоделанный кусок)

**Самая рискованная интеграция — отдельной ранней фазой** (как уже
сказано в phase-example.md). Риск определяй по разделу 10.2 ТЗ:
интеграция без подтверждённого доступа/документации — самая
рискованная почти всегда.

**Порядок данных важнее порядка экранов.** Если поле появляется
в модели данных Фазы N, а становится видимым только в Фазе M > N —
это нормально и часто правильно (см. пример `vendor_id` в
sweet-ecommerce: заведено в Фазе 1, кабинет вендора — в Фазе 7,
чтобы не переписывать все запросы каталога задним числом). Не режь
фазы по экранам ТЗ буквально — режь по зависимостям данных.

**Но это правило не освобождает фазу от собственной проверки.**
«Поле в БД без экрана» — это одно поле в модели данных. Это не то же
самое, что «целый функциональный модуль без единой возможности
проверить его глазами». Если бэкенд-логика модуля (например,
ИИ-помощник, расчёт скидок, интеграция) ложится в Фазу N, а
единственный способ увидеть, что он работает — это экран, который
появляется только в Фазе M, и M − N > 1 — это дефект нарезки, а не
нормальная зависимость данных.

Правило: **для каждой фазы, где появляется бэкенд-логика
функционального модуля, в этой же фазе (или следующей) должен быть
хотя бы минимальный проверяемый чекпоинт** — тестовый скрипт,
CLI-команда, служебный эндпоинт, заглушка в админке без полного UI —
что угодно, что позволяет разработчику и клиенту убедиться, что
логика действительно работает, не дожидаясь экрана из более поздней
фазы. Если полноценный UI объективно откладывается надолго —
заведи этот минимальный чекпоинт отдельным явным таском внутри
фазы с бэкендом (по аналогии с `[INFRA]`-таском sitemap.xml ниже) и
зафиксируй это как решение в `planning-log.md`, а не оставляй
молчаливый разрыв между фазами.

При ревью (`sdd-review`) разрыв больше одной фазы между «логика
появилась» и «логику можно увидеть» без такого зафиксированного
решения — повод вернуть роадмап на пересборку.

## Что сделать

1. Сгруппируй требования раздела 8 (`FR-*`) и раздела 9 (`BR-*`) в 5-12 фаз.
   Для `NFR-*` из раздела 11 определи: какие требуют конкретной работы в фазе
   (например, кэширование, антиспам, настройка бэкапов), а какие закрываются
   сквозным контролем (`dod-global.md`, `database.md`, `AGENTS.md`, `planning-log.md`)
   без дублирования в фазах
2. Обнови `.docs/phases/_status.md`: таблица со всеми фазами, названием,
   **колонкой «Требования ТЗ» с явными ID/диапазонами** (`FR-*`, `BR-*` и тех
   `NFR-*`, под которые запланирована работа в фазе, например `FR-CAT-001…015, BR-001`)
   и статусом `⏳ Ожидает`. Это критично: подробные `phase-N.md` появятся позже
   в `phase-init`, поэтому `check_sdd.py` проверяет назначение требований именно
   по `_status.md`
3. Если нарезка неочевидна — добавь в `_status.md` блок «Порядок не
   случайный» (по образцу sweet-ecommerce) с объяснением зависимостей
4. Допиши роадмап в `.docs/prd.md` §11 (или соответствующий раздел
   по факту структуры стартера) — списком по фазам, без детализации
   до таска (детализация — задача `phase-init`, не твоя)
5. Обнови `.docs/tz-coverage.md`:
   - для каждого `FR-*` и `BR-*` укажи номер фазы (или сквозной артефакт для сквозного `BR-*`)
   - для каждого `NFR-*` укажи конкретный механизм обеспечения (фаза или сквозной контроль)
     и способ проверки (см. формат в `reference/sdd-planning-agent.md`)

## Обязательная инфраструктурная задача — генератор sitemap.xml

> **Применимость:** только для стеков, где `sitemap.xml` генерируется кодом
> приложения (`php-ecommerce`, `laravel`). Для стека `wp-woocommerce` этот блок
> **не применяется**: там `sitemap.xml` формирует SEO-плагин (`CORE-11`),
> создавать свой или физический `sitemap.xml` запрещено.

Не требование клиента, не привязано ни к одному `FR-*`/`BR-*` — это
базовая инфраструктура стартера (в `php-ecommerce` и `laravel`), нужна **каждому**
проекту на этих стеках, независимо от того, что клиент ответил про важность SEO
в разделе 7.1 ТЗ. `database.md` уже содержит `seo_title`/
`seo_description` у публичных сущностей (`products`, `categories`,
`content_pages`) и правило их генерации — реального эндпоинта
`/sitemap.xml`, который строит XML из этих таблиц, в стартере ещё
нет, только заглушка.

Заведи для неё отдельный таск внутри той фазы, где каталог
(`products`/`categories`) уже существует в БД — не раньше, не
отдельной фазой. Обоснование: `sitemap.xml` бессмыслен без данных,
которые перечисляет, значит логическая зависимость такая же, как
у `vendor_id` в примере выше — задача не двигает фазу, она просто
не может стоять раньше своей зависимости.

Отметь этот таск в `_status.md` явной строкой (не растворяй в общем
списке модуля каталога) — он единственный не имеет `FR-*`/`BR-*` в
качестве источника, и `tz-coverage.md` его не увидит по обычному
правилу покрытия. Формат отметки:

```
[INFRA] Генератор sitemap.xml — не из ТЗ, базовая инфраструктура
стартера (database.md, правило генерации SEO-полей)
```

## Отчёт

- Сколько фаз, краткий список
- Обоснование нарезки (ссылка на приоритет 3.1 ТЗ)
- Какая фаза — самая рискованная и почему
- В какую фазу и таск попал `[INFRA]` генератор sitemap.xml
- Для каждого функционального модуля с бэкенд-логикой: в какой фазе
  появляется минимальный проверяемый чекпоинт, и не превышает ли
  разрыв между фазой логики и фазой чекпоинта одну фазу — если
  превышает, явно назови модуль и обоснование (решение из
  `planning-log.md`), а не просто пройди молча
- tz-coverage.md: все ли ID раздела 8/9 попали хоть в одну фазу —
  это критично, требование без фазы потеряется молча
- Следующий шаг: `sdd-admin` (если в стартере есть
  `public/assets/vendor/tabler/`), `sdd-modules` (если проект крупный —
  решает человек) или сразу `sdd-review`
