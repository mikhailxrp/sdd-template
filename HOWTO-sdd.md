# Как пользоваться SDD-конвейером

## Что это такое

Второй цех после ТЗ:

```
Бриф  →  ТЗ  →  SDD  →  Код
              ↑
          этот цех
```

**ТЗ** — что нужно построить (мы это уже написали в первом цехе).

**SDD** — план стройки: структура папок, схема базы данных, разбивка
на этапы работы. По этому плану потом будет писаться код.

**Код** — сюда мы не идём. SDD-цех готовит документы, а не пишет код.

---

## Главная идея

Мы не пишем структуру проекта с нуля каждый раз. У нас уже есть
готовые «болванки» под разные стеки — папки с правильной структурой,
проверенными правилами и базовой схемой базы данных. Это называется
**стек-стартер**.

Наша работа — взять такую болванку и заполнить её данными из готового
ТЗ: какие таблицы нужны, что за проект, на какие этапы его разбить.

```
Стек-стартер (пустой)  +  Готовое ТЗ  =  Заполненный план разработки
```

---

## Что лежит в папках

```
sdd-template\                     ← ЭТАЛОН, отсюда всё копируется
```

| Папка / файл                      | Что внутри                                                          |
| --------------------------------- | ------------------------------------------------------------------- |
| `stacks\`                         | Болванки под разные стеки (`php-ecommerce`, `laravel`)              |
| `reference\sdd-planning-agent.md` | Правила для агента на этапе планирования                            |
| `reference\audit-agent.md`        | Правила для агента на этапе аудита готового кода                    |
| `workflow\`                       | Единые тексты всех команд планирования и аудита (`sdd-*`, `audit-*`)|
| `.claude\commands\`               | Обёртки команд для Claude Code (ссылаются на `workflow\`)           |
| `.agents\skills\`                 | Обёртки тех же команд для Antigravity (ссылаются на `workflow\`)    |
| `tools\`                          | Проверяльщик покрытия (`check_sdd.py`) и скрипт создания проекта    |

**Важно:** `sdd-template` — это склад образцов. Работа всегда идёт
в отдельной папке проекта, не здесь.

---

## Файлы правил — не перепутайте

В ТЗ-цехе файл правил был нужен агенту, который пишет ТЗ.

Здесь по-другому. `AGENTS.md` (и подробные правила в `.docs\rules\`) в
SDD-проекте — это правила для **будущего программиста** (или агента-кодера),
который потом будет писать код. Они приходят готовыми из стек-стартера, мы
их не переписываем.

- **Antigravity** читает `AGENTS.md` напрямую.
- **Claude Code** читает `CLAUDE.md`, а тот одной строкой подключает
  `AGENTS.md` и `.docs\rules\*.md` (сам `CLAUDE.md` не редактируется).

Правила именно для планирования лежат отдельно —
в `reference\sdd-planning-agent.md`. Так мы не портим файлы, которые
нужны для следующего этапа — написания кода.

## Начало работы

### Шаг 1. Убедитесь, что ТЗ готово

Нужен проект из ТЗ-конвейера, где уже есть:

```
имя-проекта\01-tz\tz.md
```

Это то, что мы получаем в конце работы с `/tz-review`.

### Шаг 2. Создать SDD-проект

Из корня `sdd-template`:

```powershell
# Пример для стека PHP (shared-хостинг, e-commerce)
.\tools\sdd-new-project.ps1 -Name domform-sdd -Stack php-ecommerce -TzProject D:\Development\domform

# Пример для стека Laravel (VPS, модульные пакеты capabilities)
.\tools\sdd-new-project.ps1 -Name autochem-sdd -Stack laravel -TzProject D:\Development\autochem
```

Что произойдёт само:

- скопируется болванка стека `php-ecommerce`
- скопируются `reference\`, `workflow\`, `tools\`, `.claude\` и `.agents\`
- скопируется готовое ТЗ в `00-input\tz.md`
- если в ТЗ-проекте были макеты (`00-input\design\`) или реестр
  экранов (`01-tz\screens.md`) — они тоже скопируются

### Шаг 3. Открыть проект в агенте

Работает одинаково в обеих средах:

- **Claude Code:**
  ```powershell
  cd ..\domform-sdd
  claude
  ```
- **Antigravity:** открыть папку `domform-sdd` как рабочую область (workspace).

## Команды планирования по порядку

В Claude Code команды вызываются со слэшем (`/sdd-init`), в Antigravity —
по имени скилла (`sdd-init` или `/sdd-init`).

### 1. `/sdd-init` — о чём проект

Агент читает начало ТЗ (кто пользователи, какие роли, какая модель
данных) и заполняет первую часть плана — описание продукта.

**Получите:** заполненный `.docs\prd.md`, заполненный блок «О проекте» в
`AGENTS.md`, начало двух журналов: `tz-coverage.md` (что уже учтено) и
`planning-log.md` (какие решения приняты и почему).

### 1.5. `/sdd-capabilities` — сборка пакетов (для стеков с `capabilities/`, например `laravel`)

Если в стеке используется модульная архитектура пакетов (папка `capabilities\`):
агент читает таблицу «Возможности» в `.docs\prd.md`, уточняет недостающие
параметры по ТЗ, проверяет зависимости/конфликты, вставляет блоки включённых
пакетов с маркерами `capability:<name>:begin/end` в `AGENTS.md`,
`.docs\database.md`, `.docs\dod-global.md` и создаёт `.docs\capabilities.md`.
После подтверждения папка `capabilities\` удаляется из проекта. Для добавления
или удаления пакета позже используются `/sdd-capabilities add <name>` и
`/sdd-capabilities remove <name>`.

Для стека `php-ecommerce` этот шаг пропускается.

### 2. `/sdd-schema` — база данных

Агент смотрит на модель данных из ТЗ и достраивает схему базы:
добавляет колонки в существующие таблицы, создаёт новые, где нужно.

**Что проверить:** если в ТЗ было что-то необычное (например,
у каждого варианта товара свой номер, не общий на модель) — посмотрите,
появилось ли это в `database.md` отдельной таблицей, а не просто
полем.

### 3. `/sdd-roadmap` — разбивка на этапы

Самая важная команда. Агент смотрит на весь список требований
(только заголовки, не вчитываясь в каждое) и решает, в каком порядке
всё это строить.

**Получите:** заполненный `.docs\phases\_status.md` — список этапов
(«фаз») разработки.

**Что проверить:** самая рискованная часть проекта (обычно —
интеграция, для которой ещё нет доступа) должна стоять **рано**,
а не в конце. Если у вас, как в примере ДомФорм, оплата ЮMoney ещё
не проверена на совместимость с кассой — эта фаза должна быть близко
к началу, чтобы риск открылся быстро, а не после месяца работы.

### 3.5. `/sdd-admin` — план экранов админки

Только если в стеке есть Tabler (`public\assets\vendor\tabler\`). Готовых
страниц админки в шаблоне нет: Tabler — это набор компонентов (CSS, JS,
виджеты, иконки), а экраны собираются из него под ваш проект. Агент
смотрит на требования к админке и менеджерской панели из ТЗ и решает,
какие экраны нужны, не тащит всё подряд.

**Получите:** файл `.docs\admin-assembly.md` — план экранов. Для каждого
экрана указано, из каких компонентов Tabler и каких виджетов он
собирается и какие поля из `database.md` в нём показываются. Код экранов
команда не пишет, это делается позже, на этапе фаз и задач.

**Что проверить:** откройте `admin-assembly.md`. Первой строкой должен
стоять каркас админки (меню, шапка, проверка роли admin). Дальше каждая
строка должна называть конкретные компоненты и поля проекта, не просто
«сделать форму». Виджеты должны быть из реально существующих папок
`public\assets\vendor\tabler\libs\`. Если нужного виджета там нет,
агент заводит вопрос `Q-DEV`, а не подключает библиотеку с интернета.

### 4. `/sdd-modules` — только для больших проектов

Папка `.docs\modules\` не идёт в стартере заранее — она появляется
сама, когда вы **первый раз** запустите эту команду. То есть решение
не «есть папка → проект крупный», а наоборот: вы сами решаете, что
проект достаточно крупный (несколько независимых модулей со сложной
логикой — оплата, ИИ-помощники, интеграции), и запускаете команду —
тогда папка и файл создаются автоматически.

Запускается с аргументом — какой модуль расписать:

```
/sdd-modules CHK
/sdd-modules AI
```

Если проект средний — пропустите этот шаг, детализация произойдёт в `phase-init`.

### 5. `/sdd-review` — проверка готовности

**Обязательно начните новую сессию** (в Claude Code — `exit` и снова `claude`,
в Antigravity — новый чат) — как и в ТЗ-цехе, свежий взгляд видит то, что
уставший автор не замечает.

```
/sdd-review
```

Агент проверит: не забыто ли какое-то требование, не противоречит
ли схема базы данных сама себе, правильный ли порядок этапов.

---

## Проверка руками

В любой момент:

```powershell
python tools\check_sdd.py .
```

Покажет:

| Строка                            | Значение                                         |
| --------------------------------- | ------------------------------------------------ |
| `Покрыто в плане разработки: 92%` | Сколько требований из ТЗ реально учтено          |
| `Не покрыто: 8`                   | Столько требований потеряются, если не исправить |
| `Ошибок: 0`                       | Можно двигаться дальше                           |

**Если «не покрыто» не ноль** — значит, какое-то требование из ТЗ
не попало ни в одну фазу разработки. Его забудут при написании кода.
Это не мелочь — это ровно та причина, ради которой вообще ведётся
эта проверка.

## Что дальше, после SDD-цеха

Когда `/sdd-review` пройдено и `check_sdd.py` не находит ошибок —
план готов. Дальше начинается сама разработка, но это уже штатные
инструменты стартера, которые мы не трогали:

```
.docs\prompts\phase-init.md   → спланировать конкретный этап
.docs\prompts\task-init.md    → создать конкретную задачу
.docs\prompts\dod-check.md    → проверить, что задача сделана правильно
```

Их можно запускать прямо как есть — README самого стартера объясняет,
как. SDD-цех свою работу закончил: он подготовил всё, что нужно
этим командам, чтобы не переспрашивать по новой.

Когда код (или часть фаз) готов, в том же проекте доступны команды
аудита (`workflow\audit-*.md`, правила в `reference\audit-agent.md`):

- `/audit-security` — безопасность по `dod-global.md`
- `/audit-functional` — соответствие требованиям `tz.md`
- `/audit-integration` — стыки между модулями и фазами
- `/audit-seo` — SEO и GEO
- `/audit-report` — сводный отчёт `.docs\audit-report.md`

## Если что-то пошло не так

| Проблема                                                    | Что делать                                                                          |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Агент не может найти `00-input\tz.md`                       | Проверьте, что ТЗ-проект точно прошёл `/tz-review`, и путь `-TzProject` указан верно |
| В `database.md` появилась таблица, дублирующая существующую | Скажите агенту свериться с `planning-log.md` — возможно, решение уже принято раньше |
| Фазы идут в странном порядке                                | Спросите агента, почему — по правилу, он обязан объяснить зависимости в `_status.md` |
| `check_sdd.py` находит непокрытые требования                | Пройдите `tz-coverage.md`, найдите, на каком шаге их пропустили, повторите этот шаг |
| В проекте на `laravel` позже понадобился новый пакет (например, оплата) | Запустите `/sdd-capabilities add <name>` (или `remove <name>` для отключения); исходники берутся из первого коммита проекта или `sdd-template` |

---

## Три вещи, которые стоит запомнить

1. **`sdd-template` — склад, а не рабочее место.** Как и в ТЗ-цехе,
   работа всегда идёт в отдельной папке проекта.

2. **`AGENTS.md` (и `CLAUDE.md`) в SDD-проекте — не для нас.** Это правила
   для будущего кода: в `AGENTS.md` мы только заполняем «О проекте»,
   таблицу документации и (в стеке `laravel`) собираем блоки пакетов
   командой `/sdd-capabilities`, а `CLAUDE.md` вообще не трогаем.

3. **`/sdd-review` — новой сессией (или новым чатом).** Так же, как и в
   ТЗ-цехе: автор своих ошибок не видит.

## Шпаргалка

```powershell
# Новый SDD-проект (из корня sdd-template): стек php-ecommerce или laravel
.\tools\sdd-new-project.ps1 -Name имя-sdd -Stack php-ecommerce -TzProject D:\Development\имя-тз-проекта
.\tools\sdd-new-project.ps1 -Name имя-sdd -Stack laravel -TzProject D:\Development\имя-тз-проекта

# Дальше открыть ..\имя-sdd в Antigravity или запустить Claude Code:
cd ..\имя-sdd
claude
```

```
/sdd-init
/sdd-capabilities       → только для стеков с capabilities/ (например, laravel)
/sdd-schema
/sdd-roadmap
/sdd-admin              → только если в проекте есть Tabler (php-ecommerce; для Filament в laravel не нужен)
/sdd-modules <КОД>      → только для крупных проектов
                        → начать новую сессию (Claude Code: exit → claude; Antigravity: новый чат)
/sdd-review
```

```powershell
# Проверка в любой момент
python tools\check_sdd.py .
```
