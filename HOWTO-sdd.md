# Как пользоваться SDD-конвейером

## Что это такое

Второй цех после ТЗ:

```
Бриф  →  ТЗ  →  SDD  →  Код
              ↑
          этот цех
```

**ТЗ** — что нужно построить (мы это уже написали в первом цехе).

**SDD** — план стройки: структура папок, схема базы данных, разбивка
на этапы работы. По этому плану потом будет писаться код.

**Код** — сюда мы не идём. SDD-цех готовит документы, а не пишет код.

---

## Главная идея

Мы не пишем структуру проекта с нуля каждый раз. У нас уже есть
готовые «болванки» под разные стеки — папки с правильной структурой,
проверенными правилами и базовой схемой базы данных. Это называется
**стек-стартер**.

Наша работа — взять такую болванку и заполнить её данными из готового
ТЗ: какие таблицы нужны, что за проект, на какие этапы его разбить.

```
Стек-стартер (пустой)  +  Готовое ТЗ  =  Заполненный план разработки
```

---

## Что лежит в папках

```
D:\Development\sdd-template\      ← ЭТАЛОН, отсюда всё копируется
```

| Папка | Что внутри |
|---|---|
| `stacks\` | Болванки под разные стеки. Пока одна: `php-ecommerce` |
| `reference\sdd-planning-agent.md` | Правила для Claude на этапе планирования |
| `.claude\commands\` | Пять команд — кнопки, которые понимает Claude |
| `tools\` | Проверяльщик и скрипт создания проекта |

**Важно:** `sdd-template` — это склад образцов. Работа всегда идёт
в отдельной папке проекта, не здесь.

---

## Два разных «CLAUDE.md» — не перепутайте

В ТЗ-цехе `CLAUDE.md` был правилами для Claude, который пишет ТЗ.

Здесь по-другому. `CLAUDE.md` в SDD-проекте — это правила для
**будущего программиста** (или Claude), который потом будет писать
код. Он приходит готовым из стек-стартера, мы его не переписываем.

Правила именно для планирования лежат отдельно —
в `reference\sdd-planning-agent.md`. Так мы не портим файл, который
нужен для следующего этапа — написания кода.

## Начало работы

### Шаг 1. Убедитесь, что ТЗ готово

Нужен проект из ТЗ-конвейера, где уже есть:

```
имя-проекта\01-tz\tz.md
```

Это то, что мы получаем в конце работы с `/tz-review`.

### Шаг 2. Создать SDD-проект

```powershell
cd D:\Development\sdd-template
.\tools\sdd-new-project.ps1 -Name domform-sdd -Stack php-ecommerce -TzProject D:\Development\domform
```

Что произойдёт само:
- скопируется болванка стека `php-ecommerce`
- скопируется готовое ТЗ в `00-input\tz.md`
- если в ТЗ-проекте были макеты (`00-input\design\`) или реестр
  экранов (`01-tz\screens.md`) — они тоже скопируются

### Шаг 3. Открыть Claude Code

```powershell
cd D:\Development\domform-sdd
claude
```

## Пять команд по порядку

### 1. `/sdd-init` — о чём проект

Claude читает начало ТЗ (кто пользователи, какие роли, какая модель
данных) и заполняет первую часть плана — описание продукта.

**Получите:** заполненный `.docs\prd.md`, начало двух журналов:
`tz-coverage.md` (что уже учтено) и `planning-log.md` (какие решения
приняты и почему).

### 2. `/sdd-schema` — база данных

Claude смотрит на модель данных из ТЗ и достраивает схему базы:
добавляет колонки в существующие таблицы, создаёт новые, где нужно.

**Что проверить:** если в ТЗ было что-то необычное (например,
у каждого варианта товара свой номер, не общий на модель) — посмотрите,
появилось ли это в `database.md` отдельной таблицей, а не просто
полем.

### 3. `/sdd-roadmap` — разбивка на этапы

Самая важная команда. Claude смотрит на весь список требований
(только заголовки, не вчитываясь в каждое) и решает, в каком порядке
всё это строить.

**Получите:** заполненный `.docs\phases\_status.md` — список этапов
(«фаз») разработки.

**Что проверить:** самая рискованная часть проекта (обычно —
интеграция, для которой ещё нет доступа) должна стоять **рано**,
а не в конце. Если у вас, как в примере ДомФорм, оплата ЮMoney ещё
не проверена на совместимость с кассой — эта фаза должна быть близко
к началу, чтобы риск открылся быстро, а не после месяца работы.

### 3.5. `/sdd-admin` — выбор страниц админки

Только если в стеке есть готовый шаблон админ-панели
(`00-input\admin-template\`). Claude смотрит на требования к админке
и менеджерской панели из ТЗ и решает, какие из готовых страниц
шаблона реально нужны в этом проекте — не тащит всё подряд.

**Получите:** нужные страницы скопированы в проект, плюс файл
`.docs\admin-assembly.md` — список того, чего в шаблоне не было
и что придётся собрать вручную из готовых кусков (например, форму
добавления товара — из готовой формы письма с вложениями).

**Что проверить:** откройте `admin-assembly.md`. Каждая строка должна
объяснять, из какого файла шаблона собирать недостающую страницу —
не просто «сделать форму», а «взять каркас из mail-compose.html».

### 4. `/sdd-modules` — только для больших проектов

Если в стек-стартере есть папка `.docs\modules\` — значит, проект
крупный и каждую важную часть (оплата, ИИ-помощник, личный кабинет)
стоит расписать отдельным файлом.

Запускается с аргументом — какой модуль расписать:

```
/sdd-modules CHK
/sdd-modules AI
```

Если папки `.docs\modules\` нет — пропустите этот шаг, он не для
вашего проекта.

### 5. `/sdd-review` — проверка готовности

**Обязательно закройте Claude Code и откройте заново** — как и
в ТЗ-цехе, свежий взгляд видит то, что уставший автор не замечает.

```powershell
exit
claude
```
```
/sdd-review
```

Claude проверит: не забыто ли какое-то требование, не противоречит
ли схема базы данных сама себе, правильный ли порядок этапов.

---

## Проверка руками

В любой момент:

```powershell
python tools\check_sdd.py .
```

Покажет:

| Строка | Значение |
|---|---|
| `Покрыто в плане разработки: 92%` | Сколько требований из ТЗ реально учтено |
| `Не покрыто: 8` | Столько требований потеряются, если не исправить |
| `Ошибок: 0` | Можно двигаться дальше |

**Если «не покрыто» не ноль** — значит, какое-то требование из ТЗ
не попало ни в одну фазу разработки. Его забудут при написании кода.
Это не мелочь — это ровно та причина, ради которой вообще ведётся
эта проверка.

---

## Что дальше, после SDD-цеха

Когда `/sdd-review` пройдено и `check_sdd.py` не находит ошибок —
план готов. Дальше начинается сама разработка, но это уже штатные
инструменты стартера, которые мы не трогали:

```
.docs\prompts\phase-init.md   → спланировать конкретный этап
.docs\prompts\task-init.md    → создать конкретную задачу
.docs\prompts\dod-check.md    → проверить, что задача сделана правильно
```

Их можно запускать прямо как есть — README самого стартера объясняет,
как. SDD-цех свою работу закончил: он подготовил всё, что нужно
этим командам, чтобы не переспрашивать по новой.

---

## Если что-то пошло не так

| Проблема | Что делать |
|---|---|
| Claude не может найти `00-input\tz.md` | Проверьте, что ТЗ-проект точно прошёл `/tz-review`, и путь `-TzProject` указан верно |
| В `database.md` появилась таблица, дублирующая существующую | Скажите Claude свериться с `planning-log.md` — возможно, решение уже принято раньше |
| Фазы идут в странном порядке | Спросите Claude, почему — по правилу, он обязан объяснить зависимости в `_status.md` |
| `check_sdd.py` находит непокрытые требования | Пройдите `tz-coverage.md`, найдите, на каком шаге их пропустили, повторите этот шаг |

---

## Три вещи, которые стоит запомнить

1. **`sdd-template` — склад, а не рабочее место.** Как и в ТЗ-цехе,
   работа всегда идёт в отдельной папке проекта.

2. **`CLAUDE.md` в SDD-проекте — не для нас.** Это правила для
   будущего кода, мы их только дополняем, не переписываем.

3. **`/sdd-review` — новой сессией.** Так же, как и в ТЗ-цехе:
   автор своих ошибок не видит.

## Шпаргалка

```powershell
# Новый SDD-проект
cd D:\Development\sdd-template
.\tools\sdd-new-project.ps1 -Name имя-sdd -Stack php-ecommerce -TzProject D:\Development\имя-тз-проекта

cd D:\Development\имя-sdd
claude
```

```
/sdd-init
/sdd-schema
/sdd-roadmap
/sdd-admin              → только если есть шаблон админки
/sdd-modules <КОД>      → только для крупных проектов
                        → закрыть и открыть Claude Code заново
/sdd-review
```

```powershell
# Проверка в любой момент
python tools\check_sdd.py .
```
